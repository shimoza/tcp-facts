# TCP Facts 2026-10-28: elb

- Creating the pool with listener_id and leaving default_pool_id off the listener makes the pool depend on the listener in Terraform, so destroy removes the pool first and the listener second, matching the order the ELB v3 API accepts. (KB-2BL5, live, checked 2026-09-16)
- Only a dedicated load balancer can send traffic to servers outside its own VPC. With IP as a backend enabled it adds servers by private IPv4 address in a VPC linked by VPC peering or in an on-premises data centre linked by Direct Connect or VPN. (KB-36IY, docs, checked 2026-09-25)
- A server added to a dedicated load balancer by its IP address takes at most 50,000 concurrent connections. (KB-3LFE, docs, checked 2026-09-25)
- Load balancers are listed with GET /v2/{project_id}/elb/loadbalancers. The response holds loadbalancers[], and each entry carries name, id, operating_status, provisioning_status and vip_address. (KB-4XYI, live, checked 2026-09-25)
- GET /v3/{project_id}/elb/loadbalancers/{loadbalancer_id} for a dedicated load balancer that no longer exists answers HTTP 404 with error_code ELB.8904, 'loadbalancer <id> could not be found'. Seen after a terraform destroy that stopped halfway: the load balancer was gone in TCP while the Terraform state still listed it. (KB-7QDZ, live, checked 2026-10-06)
- The public price API carries a record named Shared Elastic Loadbalancer for eu-nl (seen on 2026-09-25), although section 6.5.3 of the service description shows n.a. for EU-NL and the ELB documentation allows only dedicated load balancers in eu-nl, so that record is no proof of availability. (KB-B4SW, live, checked 2026-09-25, recheck due)
- When an elastic IP is passed into opentelekomcloud_lb_loadbalancer_v3 by id, the attribute public_ip[0].address stays null, so an output that reads it fails the apply at the last step with every resource already created. (KB-BETP, live, checked 2026-09-16)
- IP as a backend cannot be switched off once it is enabled. In the v3 API the load balancer field ip_target_enable can only be updated to true. (KB-BFDT, docs, checked 2026-09-25)
- An ELB HTTPS listener presents a server certificate whose content and private key the owner uploads in PEM format, and with SNI one listener serves several domain names with their own certificates, so the TLS handshake shows the owner's domain and certificate. (KB-BNR5, docs, checked 2026-09-25)
- Servers added by IP address cannot receive the client source IP address. For HTTP and HTTPS listeners the ELB guide points to the X-Forwarded-For header instead and it names no alternative for TCP and UDP listeners. (KB-CJTJ, docs, checked 2026-09-25)
- On 2026-09-25 GET /v3/{project_id}/elb/loadbalancers on elb.eu-de returned the field ip_target_enable in the load balancer object, so the state of IP as a backend can be read back through the API. (KB-CQMN, live, checked 2026-09-25)
- DELETE /v3/{project_id}/elb/pools/{id} returns HTTP 204 while the listener that the pool belongs to still exists, which frees the listener for a later delete. (KB-DIPH, live, checked 2026-09-16)
- A shared load balancer cannot route traffic to backend servers in another VPC and cannot be used across accounts. The shared ELB API requires each member to sit in a subnet of the VPC of the load balancer. (KB-DVMF, docs, checked 2026-09-25)
- In the opentelekomcloud provider a changed certificate body on an ELB v3 certificate resource is planned as "updated in-place": the plan carries no replacement marker, and an apply would swap the certificate the listener serves. (KB-DWDN, live, checked 2026-09-17)
- On 2026-10-05 GET /v3/{project_id}/elb/flavors in eu-de listed six dedicated L7 flavors with their QPS: L7_flavor.elb.s1.small 4,000, s1.medium 16,000, s1.large 80,000, s2.small 8,000, s2.medium 40,000 and s2.large 160,000, plus L4 flavors s1 and s2 in small, medium and large. Terraform's l7_flavor takes the flavor id, which the data source opentelekomcloud_lb_flavor_v3 finds by name. (KB-E2KU, live, checked 2026-10-05)
- A shared ELB v2.0 in eu-de with an HTTP listener on port 80, a ROUND_ROBIN pool and an HTTP health monitor marked an ECS backend ONLINE within about 20 s of the monitor create, once the web server on the backend answered. The backend security group let port 80 in from the subnet range and from 100.125.0.0/16; which of the two the health checks use was not proven. (KB-EGHR, live, checked 2026-10-12)
- The shared ELB v2.0 API in eu-de accepts AK/SK calls signed SDK-HMAC-SHA256 without an X-Project-Id header: the creates of load balancer, listener, pool, member and health monitor answered 201, the deletes 204, and a read after the delete answered 404. (KB-ERDD, live, checked 2026-10-12)
- A backend member of a dedicated load balancer in eu-de that has nothing listening yet shows operating_status OFFLINE with reason_code CONNECT_FAILED in GET /v3/{project_id}/elb/pools/{pool_id}/members, and the HTTPS listener then answers 502. In a run on 2026-10-06 the server was created at 12:43 UTC, cloud-init reached modules:final at 12:44:51, nginx was being installed at about 12:45:06 and the member read ONLINE with the site answering 200 at 12:45:28: about two and a half minutes from terraform creating the server to a working site. (KB-ESMU, live, checked 2026-10-06)
- The ELB v3 certificate create at POST /v3/{project_id}/elb/certificates accepts both RSA and ECDSA certificates. (KB-FA4K, live, checked 2026-05-26)
- DELETE /v3/{project_id}/elb/listeners/{listener_id} on a dedicated load balancer answers 409 ELB.8907 'pool <id> is using this listener' while a pool is bound to the listener, also when the pool has no members left. Deleting the pool first frees the listener. In Terraform, bind the pool with listener_id on the pool resource instead of default_pool_id on the listener: then destroy deletes the pool before the listener; with default_pool_id it tries the listener first and stops. (KB-GTIT, live, checked 2026-10-06)
- A dedicated load balancer binds an existing elastic IP through public_ip { id = ... } and an SNAT rule binds one through floating_ip_id, so addresses allocated in a separate stack keep their ids and their DNS record across destroy and re-apply of the consuming stack. (KB-GZM3, live, checked 2026-09-16)
- Shared load balancers cannot be created in eu-nl. Only dedicated load balancers can be created there, on the console or through the API. (KB-H34Q, docs, checked 2026-09-25, recheck due)
- T Cloud Public (TCP) offers load balancing at layer 4 and layer 7 through Elastic Load Balancer (ELB): network load balancing for TCP and UDP and application load balancing for HTTP and HTTPS, as shared or dedicated load balancers, with dedicated ones spread over up to three availability zones. (KB-HZXL, docs, checked 2026-10-11)
- L7 rules of a policy are listed with GET /v3/{project_id}/elb/l7policies/{policy_id}/rules. Each rule carries id, type such as PATH, HOST_NAME or HEADER, compare_type such as STARTS_WITH or EQUAL_TO, value, conditions and invert. (KB-ICS6, live, checked 2026-09-25)
- On 2026-09-25 GET /v3/{project_id}/elb/flavors in eu-de returned 17 dedicated load balancer flavors over five types: L4 (6), L7 (6), L7_elastic (3), L4_elastic_max (1) and L7_elastic_max (1). This is what the listing showed on that date. (KB-J3DZ, live, checked 2026-09-25, recheck due)
- A dedicated ELB v3 load balancer create expects vip_subnet_cidr_id to hold the neutron subnet id; with the VPC subnet id the VIP is not placed. The mapping comes from GET /v1/{project_id}/subnets/{vpc_subnet_id}, whose response carries neutron_subnet_id. (KB-KG3S, live, checked 2026-05-26)
- A dedicated load balancer sends its health checks, and for HTTP or HTTPS listeners the forwarded traffic, from IP addresses in its own backend subnet, so the backend servers' security group must allow that subnet on the service and health check ports. A shared load balancer uses 100.125.0.0/16 instead. (KB-KHNT, docs, checked 2026-10-06)
- ELB v3 returns l4_flavor_id and l7_flavor_id as UUIDs, resolved through GET /v3/{project_id}/elb/flavors, which returned 17 records on 2026-09-17 with names of the form L4_flavor.elb.s1.small and L7_flavor.elb.s1.small. (KB-KK7Q, live, checked 2026-09-17)
- Through the v3 API such a server is added as a member with a private IPv4 address and without subnet_cidr_id. The API reference allows it only in backend server groups with protocol TCP, HTTP or HTTPS (the console guide also names UDP) and answers ELB.8939 while ip_target_enable is false. (KB-KKT4, docs, checked 2026-09-25)
- The ELB v3 API rejects deletion of a listener while a pool still points at it, with 409 ELB.8907 "pool <id> is using this listener". The stack applies and serves traffic, the failure appears at teardown. (KB-KZUN, live, checked 2026-09-16)
- The ELB FAQ and the v3 API also allow IP backends in a VPC of another region that is linked by a Cloud Connect cloud connection. Cloud Connect is listed under preview and beta versions in the service description, section 3.12.6. (KB-LD5O, docs, checked 2026-09-25, recheck due)
- For an L7 rule created with conditions and no top-level value, the v3 API returns value as an empty string and the match values in the conditions array, one per entry, in an order of its own: two conditions came back reversed on 2026-09-25. A rule created with a value and conditions returns that value. (KB-LJKN, live, checked 2026-09-25)
- In the opentelekomcloud Terraform provider an HTTPS listener takes its server certificate through default_tls_container_ref, which must hold the id of an opentelekomcloud_lb_certificate_v3 resource created with the fields certificate, private_key and domain. TLS terminates at the load balancer listener. (KB-MPJZ, live, checked 2026-09-16)
- The v3 rule listing and the v3 single-rule-by-id call return identical rule data for an L7 rule, conditions included. (KB-NAR6, live, checked 2026-09-25)
- On T Cloud Public (TCP) in eu-de the ELB v3 call GET /v3/{project_id}/elb/certificates returns HTTP 200 and delivers the certificate list under the response key certificates. (KB-OACX, live, checked 2026-07-02)
- Security group rules of servers added by IP address must allow traffic from the backend subnet of the load balancer, otherwise health checks fail. The ELB FAQ asks for at least 16 free IP addresses in the subnet where the load balancer resides to enable IP as a backend. (KB-OEB6, docs, checked 2026-09-25)
- A dedicated load balancer placed in eu-de-01 or eu-de-02 reaches backend servers sitting in eu-de-03 across availability zones inside the same VPC. (KB-OVNG, docs, checked 2026-09-25)
- Rebuilding an ELB in another project includes creating the backend pools and their members again. (KB-OVTY, docs, checked 2026-09-25)
- ELB L7 policies are listed with GET /v3/{project_id}/elb/l7policies using limit (default and maximum 2000) and marker paging; the response holds l7policies[] plus page_info with current_count and previous_marker; next_marker appears only when the server offers another page. In eu-de on 2026-09-25 a short page did not mean the end of the list: with limit=2 the first page held 1 of 3 policies and carried no next_marker, while the default limit returned all 3. (KB-P5PW, live, checked 2026-09-25)
- POST /v3/{project_id}/elb/certificates expects the body wrapped in a certificate object. A flat body returns HTTP 400 "Invalid request body: Error map format". The inner fields are name, type (server), domain, certificate and private_key. (KB-PJVB, live, checked 2026-05-26)
- GET /v3/{project_id}/elb/availability-zones on eu-de returned eu-de-01 and eu-de-02 on two separate tenants. The service description states up to three availability zones, which is a contractual maximum and not the zone list this endpoint returned. (KB-QQBS, live, checked 2026-10-05)
- A forwarding policy of a dedicated ELB takes one rule per rule type: on 2026-09-25 a second PATH rule on the same policy was refused with HTTP 409 ELB.8907 (already has rules with type PATH), while a HOST_NAME rule next to it was accepted. (KB-ROUV, live, checked 2026-09-25)
- On 2026-07-02 GET /v3/{project_id}/elb/availability-zones in eu-de returned exactly two zones, eu-de-01 and eu-de-02, both in state ACTIVE. Dedicated load balancer placement on that date followed this listing. (KB-SBUW, live, checked 2026-09-25, recheck due)
- Each L7 policy returned by the v3 listing carries id, name, action, listener_id, redirect_pool_id, redirect_url_config and priority. (KB-TQG5, live, checked 2026-09-25)
- A TERMINATED_HTTPS listener on ELB requires the TLS certificate to be uploaded into the target project before the listener is created. (KB-U47A, docs, checked 2026-09-25)
- The resource opentelekomcloud_lb_loadbalancer_v3 exposes the public address of a dedicated load balancer as public_ip[0].address. (KB-YFA5, live, checked 2026-09-16)
- For multi-condition L7 rules the v2 rules endpoint returns an empty value string and its response body carries no conditions array, so the match value of such a rule is not present in the v2 response; the v3 response carries it in conditions. (KB-YNV3, live, checked 2026-09-25)
- Dedicated load balancers and public NAT gateways are offered in eu-nl. On 2026-09-25 the ELB v3 flavor list of eu-nl returned the same 17 dedicated flavors as eu-de, the ELB AZ list returned eu-nl-01, eu-nl-02 and eu-nl-03, and the public NAT API (GET /v2.0/nat_gateways) answered in eu-nl. (KB-ZABN, live, checked 2026-09-25, recheck due)
- Elastic Load Balancer (ELB) distributes incoming traffic across several backend servers, checks their health and works with Auto Scaling. It is offered as shared and as dedicated load balancers for application load balancing at layer 7 and network load balancing at layer 4; a dedicated load balancer has its own resources, can span up to three availability zones and comes in fixed and elastic flavors. The documentation states that eu-de offers dedicated and shared load balancers and eu-nl offers dedicated ones. (KB-ZYJM, contract, checked 2026-10-14)
