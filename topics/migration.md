# TCP Facts 2026-10-28: migration

- In POST /v3/{project_id}/jobs/batch-creation the subnet of the DRS replication instance is passed in the field customize_sutnet_id, spelled sutnet. A body that spells the field subnet leaves it unread, and DRS places the replication instance in a subnet of its own choice. (KB-46C6, live, checked 2026-02-04, recheck due)
- After a failed or forcibly stopped DRS PostgreSQL task (DELETE /v3/{project_id}/jobs/batch-jobs with delete_type terminate or force_terminate) its logical replication slot can stay on the source. The DRS docs drop it with SELECT pg_drop_replication_slot('<slot>') as the task's own source database user; on RDS for PostgreSQL root also has the Replication attribute. (KB-5WJI, docs, checked 2026-09-25)
- MRS 3.3.0-LTS.1 and 3.5.0-LTS ship Spark 3.3.1, the same Spark 3.3 line that AWS Glue 4.0 uses, so porting Glue 4.0 PySpark code to MRS needs no Spark version jump. (KB-74US, docs, checked 2026-09-25, recheck due)
- In POST /v3/{project_id}/jobs/batch-connection each entry of the jobs array tests one endpoint of a task, with end_point_type "so" for the source and "ta" for the target. The examples in the API reference send one endpoint per request. (KB-BSBV, docs, checked 2026-09-25)
- The DRS job list, POST /v3/{project_id}/jobs, returns the total number of jobs in total_record. On 2026-09-25 the answer carried no count field at all (in February count came back as 0), so paging has to use total_record. (KB-BSE2, live, checked 2026-09-25)
- Per the DRS API reference the incremental replication delay incre_trans_delay is read with POST /v3/{project_id}/jobs/batch-progress, a call separate from batch-detail and batch-status. The error fields error_code and error_message come back from POST /v3/{project_id}/jobs/batch-status and also in each batch-detail result. (KB-BZUP, docs, checked 2026-09-25)
- In the DRS batch-connection step a source endpoint that presents no TLS certificate is created with ssl_link set to False. (KB-D5FE, docs, checked 2026-09-25)
- The flag is_sync_re_edit belongs to paused or edited DRS tasks, and a plain restart of a failed incremental task is sent without it. After the retry, batch-status shows the task back in INCRE_TRANSFER_STARTED or FULL_TRANSFER_STARTED. (KB-E5HH, live, checked 2026-02-04, recheck due)
- Both the source and the target endpoint objects need a project_id field in the DRS batch-modification step. (KB-GBEV, live, checked 2026-02-04, recheck due)
- Per the task creation process in the DRS API reference a real-time synchronization task is set up with calls under /v3/{project_id}/jobs/ in this order: batch-creation returns the task id in results[].id, batch-connection tests the endpoints, batch-modification sets the source and target endpoints, batch-sync-policy sets the DDL options ddl_trans and filter_ddl_policy, batch-select-objects picks the objects, then batch-precheck with polling of batch-precheck-result before batch-starting. (KB-GVBD, docs, checked 2026-09-25)
- A failed DRS task is restarted with POST /v3/{project_id}/jobs/batch-retry-task, which answers HTTP 200 on success. The task is named in the body by the field job_id. On 2026-09-25 a body that named the field id was refused with HTTP 400 DRS.M00201 (the parameter job_id is empty), no longer the silent no-op seen in February. (KB-HEEM, live, checked 2026-09-25)
- A DRS full+incremental task from PostgreSQL creates a logical replication slot on the source and drops it when the task completes. After a forced stop or an internal pre-check error the slot can stay and keeps WAL on the source until it is dropped by hand. (KB-I3YN, docs, checked 2026-09-25)
- DRS jobs are listed with a POST to /v3/{project_id}/jobs whose body carries cur_page, per_page and db_use_type, all three mandatory in the API reference, with cur_page 0 returning all items. The response holds jobs[] and total_record, the total number of tasks. (KB-IKQD, docs, checked 2026-09-25)
- Each batch-detail result carries name, id, status, source_endpoint with ip, db_port and db_user, target_endpoint with ip, db_port, inst_name and inst_id, and target_root_db with db_name. (KB-KEZA, docs, checked 2026-09-25)
- The DRS batch-detail call is a POST to /v3/{project_id}/jobs/batch-detail with a jobs list of ids and an optional page_req object holding cur_page and per_page. The page size per_page defaults to 5, goes up to 100 and returns all ids at 0, so a request with more than five ids and no per_page gets only the first five results on page 1. (KB-LK4Y, docs, checked 2026-09-25)
- A DRS job for PostgreSQL does not synchronize database-level privileges. Grants made with GRANT on DATABASE are missing at the destination, where the databases carry only the owner grant and the pg_database_owner grant. (KB-LWS5, live, checked 2026-02-04, recheck due)
- DRS batch status is a POST to /v3/{project_id}/jobs/batch-status with a jobs list of ids and an optional page_req whose per_page defaults to 5 and goes up to 100. Per the API reference each entry of the results list carries id, status, error_code and error_message; incre_trans_delay is documented only for batch-progress, although a live call on 2026-02-04 saw it in the batch-status results. (KB-MED3, docs, checked 2026-09-25)
- Creating a DRS task over the API runs as a sequence of calls: batch-creation, batch-connection, batch-modification, batch-select-objects, batch-precheck and batch-starting. Source and target connections are tested in separate batch-connection calls. (KB-RJTE, docs, checked 2026-09-25)
- Each job object returned by the DRS job listing carries name, id, status, engine_type and job_direction. (KB-VBW2, docs, checked 2026-09-25)
