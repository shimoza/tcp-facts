# TCP Facts 2026-10-12: evs

- Elastic Volume Service (EVS) provides block storage volumes that are attached to Elastic Cloud Servers as system or data disks; up to 32 volumes can be attached to one server and a volume can be expanded online when the operating system supports it. The disk types are High I/O, GP SSD, GP SSD V2, Ultra-High I/O and Extreme SSD, and the documentation states that system and data disks support encryption, snapshots and backups. The Regions and Endpoints page lists API endpoints for EVS in eu-de and eu-nl. (KB-2DY5, contract, checked 2026-10-11)
- On a Linux ECS an attached EVS data disk appears as a virtio block device such as /dev/vdb. A file system is created on the device before it is mounted. (KB-3URW, live, checked 2026-05-01)
- Releasing an attached EVS volume takes two calls in two different services. Detach runs through the ECS API as DELETE /v1/{project_id}/cloudservers/{server_id}/detachvolume/{volume_id} and is asynchronous, so its job must reach SUCCESS first. Only then does DELETE /v2/{project_id}/cloudvolumes/{volume_id} on the EVS API remove the volume. (KB-4V7Z, live, checked 2026-05-01)
- EVS shared disks on T Cloud Public (TCP) support SCSI-3 reservations and can be attached to up to 16 servers. The attached ECS instances have to sit in an anti-affinity ECS group. (KB-4WQV, docs, checked 2026-08-24)
- A 430 GB AWQ-INT4 model cold-load took 50 to 180 minutes from a GPSSD volume and about 7 minutes from an ESSD volume on the same GPU instance type. (KB-56WX, live, checked 2026-05-07)
- An 80 GiB restored Windows system disk reported 0 percent lazy loading at 13 s, 6 percent at 137 s and 100 percent at 438 s after the create call, while RDP answered at about 149 s. The counter is non-monotonic near the end, only the final value is reliable. (KB-5DQ4, live, checked 2026-09-02)
- An EVS data disk attached to a Windows Server 2019 or 2022 ECS supports ReFS block cloning. Backup software reported fast cloning as supported after the volume was formatted ReFS with GPT, a 64 KB cluster size and integrity streams off. (KB-6Z6K, live, checked 2026-04-22)
- EVS encryption happens at the volume layer, so an encrypted data disk is partitioned, formatted and mounted inside a Linux guest exactly like an unencrypted one. (KB-7ZUP, live, checked 2026-06-15)
- POST /v2.1/{project_id}/cloudvolumes creates an EVS volume asynchronously and returns a job_id. That job is polled on the EVS jobs endpoint /v1/{project_id}/jobs/{job_id} rather than the ECS jobs endpoint, and the new volume id appears as entities.volume_id once the job status is SUCCESS. (KB-CZH3, live, checked 2026-05-01)
- Lazy-loading progress of a restored disk is read with GET /v3/{project_id}/os-vendor-volumes/{volume_id}/internal-info. The live response carries the field lazyloading_progress, while the documentation names the field loading_progress. (KB-DLKD, live, checked 2026-09-02)
- The TCP service description states that up to 32 block storage devices may be assigned per Elastic Cloud Server, while the ECS user manual states 24 at creation and up to 60 after attachment (VBD max 24, SCSI max 59, VBD plus SCSI at most 60). The two sources disagree and neither number is settled. (KB-DMN5, docs, checked 2026-09-02)
- A volume create request on the EVS path /v2.1/{project_id}/cloudvolumes carries availability_zone in the volume body, for example eu-de-01, and the volume is created in that AZ. (KB-FSXW, live, checked 2026-05-01)
- An EVS disk consumed in CCE through a dynamic PV is bound to one AZ and can be mounted by one pod at a time. (KB-GZTZ, docs, checked 2026-09-16)
- Data of a disk restored from CBR loads lazily from OBS after the mount. A full read took 183 seconds for 8 GiB and 1780 seconds for 81 GiB, about 22 seconds per GiB or roughly 47 MB/s, and it applies per disk. (KB-HJKW, live, checked 2026-09-02)
- On a running Linux ECS with a virtio_blk system disk (ext4 on GPT), an extended EVS system disk grows online with growpart and resize2fs, without reboot. Verified from 30 GB to 100 GB while the filesystem was mounted. (KB-HNAB, live, checked 2026-06-08)
- A root EVS volume on a running ECS can be extended online. After the cloud-side extend, growpart on the root device followed by resize2fs grows a mounted ext4 partition while the instance keeps running, verified from 30 GB to 100 GB on a virtio_blk GPT disk. (KB-IP25, live, checked 2026-06-08)
- EVS General Purpose SSD (GPSSD) behaved like a burst-credit volume similar to AWS gp2 in a test: fresh volumes burst above baseline, and after hours of heavy reads sustained reads fell to about 21 MB/s (small random reads, about 285 IOPS). That made loading large model weights disk-bound. (KB-JKEF, live, checked 2026-05-07)
- EVS GP SSD v2 bills on three separate meters on TCP: provisioned capacity, provisioned IOPS above the 3,000 IOPS included, and provisioned throughput above the 125 MiB/s included. (KB-JN3T, contract, checked 2026-09-09)
- Bringing a 10 GiB GPT data volume back on a Windows Server 2022 guest took 43 s in total: 6 s to create the volume from the CBR backup, 12 s to attach it, the rest to bring it online. The volume arrives Offline under the SAN policy OfflineShared. (KB-KQUM, live, checked 2026-09-02)
- Data disks under heavy write survive a crash-consistent capture by both SDRS mirroring and CBR backup: both copies reported Filesystem state clean, mounted, and passed e2fsck -fn. The file count differs between the copies, which is expected for a point-in-time capture. (KB-KUQ7, live, checked 2026-09-02)
- A CBR backup can be restored into another availability zone: POST /v2/{project_id}/cloudvolumes on the EVS endpoint accepts backup_id together with a target availability_zone, volume_type and size, and creates the disk there. (KB-LXHJ, live, checked 2026-08-26)
- An EVS snapshot stays bound to its source volume and goes away with it, so a copy that has to outlive the disk is taken as an IMS system disk image or a CBR backup. (KB-MDYY, live, checked 2026-07-29)
- In eu-de the EVS volume listing GET /v2/{project_id}/cloudvolumes/detail returns count and volumes, and each entry carries id, name, size, volume_type, bootable and a metadata object. The metadata carries __system__encrypted on some volumes only, with value 1 or 0, and __system__cmkid only on encrypted volumes, while the top-level encrypted field read false even on encrypted volumes (checked 2026-09-25). (KB-O5MK, live, checked 2026-09-25)
- The size of the volume actually attached to an ECS is read from the EVS cloudvolumes/detail response, matching attachments[].server_id against the instance UUID from the metadata service at /openstack/latest/meta_data.json. A guest still enumerating the old size after a clean boot points to a volume that was not extended. (KB-P3SX, live, checked 2026-06-08)
- On an ECS with virtio_blk disks, the guest picks up an extended EVS volume size automatically through a virtio config-change interrupt. /sys/class/block/vda/size shows the new size before growpart is run. (KB-RGHC, live, checked 2026-06-08)
- ESSD was available in eu-de-01 when checked. The volume types offered per availability zone are listed by GET https://evs.eu-de.otc.t-systems.com/v3/{project_id}/types. (KB-SOBS, live, checked 2026-09-25)
- An EVS snapshot moves from creating to available on GET /v2/{project_id}/snapshots/{snapshot_id}. For a 40 GB GPSSD root disk that took about five seconds. (KB-SY3Y, live, checked 2026-07-29)
- A virtio_blk disk picks up a new volume size through a virtio config-change interrupt once the volume was really extended. The kernel view can be read from /sys/class/block/<dev>/size or with fdisk, and it already shows the new capacity when the event arrived. (KB-T4IL, live, checked 2026-06-08)
- EVS Extreme SSD reaches at most 1,000 MiB/s and 128,000 IOPS with sub-millisecond latency, but its throughput is Min(1,000, 120 + 0.5 x capacity in GiB): the full rate, which loads a 430 GB model in about 7 minutes, needs a disk of about 1,760 GiB, while a disk sized just for the model gets about 320 MiB/s. Extreme SSD also has an IOPS burst token bucket (burst limit 64,000) and General Purpose SSD is capped at 250 MiB/s. (KB-TUFK, docs, checked 2026-09-25)
- Creating an EVS volume from a CBR backup takes about 6 to 7 s and barely depends on volume size, measured at 8 GiB and at 81 GiB. Volume size affects the background lazy load, not the create step. (KB-UH3H, live, checked 2026-09-02)
- POST /v2/{project_id}/snapshots on EVS needs force set to true when the source volume is attached to a server; without it the request for an in-use volume is refused. The call returns HTTP 202 with a snapshot id in status creating. (KB-UQLA, live, checked 2026-07-29)
- On a Linux guest, reading a restored volume end to end took 183 s for 8 GiB and 1780 s for 81 GiB while the background load was still running. (KB-V2AA, live, checked 2026-09-02)
- Deleting an EVS disk deletes all data of the disk including the snapshots created from it, so an EVS snapshot does not outlive its source disk as it would in plain Cinder. An EVS snapshot is not an independent copy. (KB-W5BY, live, checked 2026-07-29)
- EVS volumes are triple-replicated on the platform side, so capacity is planned at net capacity: a mirrored pair of two 3.84 TB on-premises disks corresponds to about 3.84 TB of EVS, not 7.68 TB. (KB-WKHA, docs, checked 2026-09-25)
- After hours of heavy reads a GPSSD volume drained its burst credits and sustained reads fell to about 21 MB/s (iostat -x showed about 285 IOPS at roughly 10 ms r_await), against a baseline near 150 MB/s. An ESSD volume in the same test sustained about 1 GB/s with sub-millisecond latency. (KB-XXZV, live, checked 2026-05-07)
- Deleting an EVS volume also deletes the snapshots taken from it, so a snapshot lives only as long as its source disk. An IMS image or a CBR backup survives deletion of the source instance. (KB-YENF, live, checked 2026-07-29)
- An EVS data volume created from the backup child of an encrypted volume together with a destination KMS key comes up encrypted at the destination, without an OS-level copy of the data. (KB-YEPK, docs, checked 2026-09-25)
- The EVS path /v3/{project_id}/cloudvolumes/detail returns HTTP 404 in TCP eu-de. The same volume detail listing is served by the v2 path. (KB-YIBL, live, checked 2026-09-25)
