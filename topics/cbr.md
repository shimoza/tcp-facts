# TCP Facts 2026-10-28: cbr

- A crash-consistent restore of a Windows ECS backed up during continuous writes contained one truncated file out of 37, while a comparison run with writes stopped and the volume cache flushed before the backup contained zero damaged files out of 57. (KB-3PZR, live, checked 2026-09-02)
- Creating a CBR vault with consistent_level app_consistent returns HTTP 400 with error code BackupService.6126, while crash_consistent returns 200. The API enum accepts both values. Checked on a vault with object_type server. (KB-3T3I, live, checked 2026-09-02)
- CBR keeps backup copies inside its own vaults. The service overview constraints page lists download of a backup to a local PC and upload of a backup to OBS as operations the service excludes. Vault locking therefore protects only the copies held in CBR. (KB-47P2, docs, checked 2026-09-16)
- Removing a protected resource from a CBR vault lowers the vault's `allocated` value on its own. One vault went from 190 GB to 140 GB after a resource was removed, with only the removal call. (KB-4HSQ, live, checked 2026-09-16)
- A Linux ext4 root filesystem captured while the server was running failed to boot after restore: the clone superblock read clean with errors and ext4_orphan_get reported EFSCORRUPTED. Restored from a backup of the same server taken while stopped, it booted in 66 seconds with a clean superblock. (KB-6CUR, live, checked 2026-09-02)
- A Linux server restored from an enhanced CBR backup reached service in 31 to 33 seconds independent of data volume: disk handed over in 6 to 7 seconds by Instant Restore, standby start 11 seconds, attach 12 seconds, mount 3 to 5 seconds. Instant Restore requires an enhanced backup, readable as support_lld. (KB-6DKR, live, checked 2026-09-02)
- The CBR documentation describes no deduplication and no calculator for storage per backup frequency. CBR stores block-level incremental-forever backups that reference unchanged blocks, and the guide says backup sizes cannot be estimated from file sizes. (KB-6EHO, docs, checked 2026-10-22)
- The units in a CBR vault payload are mixed: `billing.size` and `billing.allocated` are GB, while `billing.used` is MB. Reading `billing.used` as GB turns 155588 MB into an apparent 155 TB. (KB-6IRS, live, checked 2026-09-16)
- After a CBR server restore a logical volume group has to be attached again, and the CBR FAQ covers a login password that became random after a restore or after creating a server from an image and points to the ECS password reset. (KB-73MN, docs, checked 2026-09-25)
- A cold rebuild from backup to a working service measured 111 s with a Debian guest and 149 to 168 s with Windows Server 2022. The Debian figure holds only for a backup taken from a stopped machine. Different phases and disk sizes, so an order of magnitude, not a controlled comparison. (KB-7DCC, live, checked 2026-09-02)
- A volume restored from a CBR backup is usable at once through Instant Restore and loads its blocks lazily in the background, so full read speed comes later. This applies to every restored data volume, not only to the system volume of a machine rebuilt from an image. (KB-BNJP, live, checked 2026-09-02)
- CBR backups are created with consistent_level crash_consistent. A request for app_consistent is rejected by the service with error BackupService.6126. (KB-C2ML, live, checked 2026-09-02)
- When accepting a shared CBR backup, the member_id in the accept path is the destination project id. The member UUID returned in the share response is rejected with 404 BackupService.6705. (KB-C4AO, docs, checked 2026-09-25)
- Deleting a CBR vault that holds backups is asynchronous in eu-de: after DELETE /v3/{project_id}/vaults/{vault_id} the vault reported billing.status deleting, its used capacity dropped to 0 after about a minute and the vault answered 404 BackupService.6105 'Vault Not Found' after about three minutes. A vault without backups was gone at the first check. (KB-CNKG, live, checked 2026-10-05)
- A pilot light switchover (start the stopped standby, create one data volume from a CBR backup, attach it and bring it online) measured 31 to 33 s with a Debian guest and 66 s with a Windows Server 2022 guest. (KB-D5LC, live, checked 2026-09-02)
- Per the EVS user guide a disk created from a CBR backup is encrypted or not by a choice made at creation, while the EVS API reference says a create call without __system__encrypted gives the new disk the encryption attribute of its data source. A live restore of an encrypted volume on a test tenant in eu-de on 2026-02-04 produced a target volume with the encryption flag off. (KB-DESF, docs, checked 2026-09-25)
- An EVS root volume restored from a CBR backup that was taken while the machine was running failed to boot in 3 of 3 attempts on Debian with ext4. The same path on Windows Server 2022 with NTFS booted, and chkdsk reported no errors. (KB-DKE3, live, checked 2026-09-02)
- The restore point of a CBR backup sits at the start of the backup run. A source counter that moved from 220 to 412 during a 304 s backup came back at 234 on the restored disk, so RPO counts from the backup start. (KB-E435, live, checked 2026-09-02)
- A CBR vault keeps its resource binding after the bound ECS is deleted: on 2026-10-05 a server vault and a disk vault in eu-de still listed the server (OS::Nova::Server) and its volume (OS::Cinder::Volume) with protect_status available, while the ECS server listing no longer returned that server. A cleanup by resource therefore has to look at the vaults as well. (KB-EBMP, live, checked 2026-10-05)
- In a CBR vault, size is the configured capacity in GB, billing.allocated is the sum of the sizes of the protected resources rather than the vault capacity, and billing.used is in MB. (KB-EQOS, live, checked 2026-09-17)
- A CBR backup policy accepts several execution times per day, on or off the hour. With a day-based retention rule CBR keeps only the latest backup of each day, and a backup that runs past the next execution time makes CBR skip that time. (KB-GG7D, docs, checked 2026-10-22)
- CBR vault backup locking keeps automatic backups undeletable by any user for the whole retention period, stays enabled once switched on, leaves manual backups deletable, and still allows cross-region replication of the locked vault. (KB-I63S, docs, checked 2026-09-01)
- CBR vault creation documents crash_consistent as the consistency level value, and the CBR service overview describes CBR backups as crash-consistent. (KB-IJTE, docs, checked 2026-09-02)
- T Cloud Public (TCP) runs scheduled backups with a set retention period: a Cloud Backup and Recovery (CBR) backup policy runs on chosen weekdays or every 1 to 30 days at a set time and keeps backups by count or for one month, three months, six months, one year or a custom period of 2 to 99,999 days, with optional weekly, monthly and yearly long-term rules. RDS databases are backed up automatically every day by default and kept for 1 to 732 days. (KB-ITGL, docs, checked 2026-10-11)
- Restoring a CBR server backup stops the server and starts it again when the restore ends unless Start the server immediately after restoration is deselected, and the backup overwrites the current disks, by default the original ones or another disk of at least the same size. (KB-K6HK, docs, checked 2026-09-25)
- In a CBR vault object the billing.size field is the capacity in GB, while billing.used is the used capacity in MB (API reference: 'Used capacity, in MB'). A disk vault of size 10 with used 3084 holds about 3 GB, not more than its capacity. (KB-LGK7, docs, checked 2026-10-05)
- CBR backup deletion is asynchronous: delete calls return success while the backups move to state `deleting`, and a list call issued right after still counts all of them. They drain to zero in about 60 seconds. A resource removed from a vault sits at `protect_status: removing` for the same window. (KB-MYLM, live, checked 2026-09-16)
- A CBR vault created with POST /v3/{project_id}/vaults protects disks when billing.object_type is disk and the resource entries use type OS::Cinder::Volume. Whole-server protection uses the resource type OS::Nova::Server instead. (KB-PP2P, live, checked 2026-08-26)
- Encryption of a volume created from a CBR backup is decided when the volume is created, since per the EVS documentation the encryption attribute of a disk cannot be changed afterwards. For an encrypted backup shared into another tenant the CBR documentation also requires the key to be shared with the recipient. (KB-Q6ES, docs, checked 2026-09-25)
- A CBR backup of a Windows Server 2022 ECS taken while the guest wrote continuously to the NTFS system disk restored to a machine that booted, reported the dirty bit as NOT Dirty, logged a healthy volume event and passed a read-only chkdsk. (KB-SPKE, live, checked 2026-09-02)
- A CBR vault can be shrunk: PUT /v3/{project_id}/vaults/{vault_id} with {"vault":{"billing":{"size":300}}} returned 200, the vault reported 300 GB at once and the existing backups stayed intact. The new size has to stay above billing.used. (KB-TWYK, live, checked 2026-09-17)
- Cloud Backup and Recovery (CBR) provides backup and restore for Elastic Cloud Servers, Elastic Volume Service disks and SFS Turbo file systems: the customer backs up all or selected volumes of a server, sets the execution time of automated backups and their retention period, and can replicate server backups to the other region. Backups are stored in vaults, the first backup is full and later ones are incremental, and backup policies set timing, frequency and retention. The Regions and Endpoints page lists API endpoints for CBR in eu-de and eu-nl. (KB-Y4LS, contract, checked 2026-10-14)
- CBR backups are incremental after the first one. A second backup of the same 81 GiB server took 243 seconds against 501 seconds for the first, which ran at roughly 3.5 seconds per GiB plus about 220 seconds fixed. (KB-YC6H, live, checked 2026-09-02)
