# TCP Facts 2026-10-10: cts

- PUT /v3/{project_id}/tracker refuses compress_type in upper case with error CTS.0227 'The compress_type must be json or gzip'; the lower-case value gzip is accepted. (KB-2QGH, live, checked 2026-09-23)
- CTS in eu-de records public NAT gateway operations under service_type VPC (deleteSnatRule, deleteNatGateway, updateFloatingip, deleteEip), not under NAT: a query with service_type=NAT for the same window returned no traces. (KB-3XKX, live, checked 2026-10-06)
- CTS in eu-de does not record an ELB API call that the service rejects: a DELETE of a listener answered 409 ELB.8907 left no trace, while the successful deletes around it did. A gap in the trail can therefore hide a failed call; the client output is the evidence for errors. (KB-4QFE, live, checked 2026-10-06)
- CTS writes transferred trace files under CloudTraces/{region}/{yyyy}/{mm}/{dd}/system/{SERVICE}/ when is_sort_by_service is true. The file_prefix_name is not a folder: it starts the file name, as in {prefix}_CloudTrace_{region}_{timestamp}Z_{hash}. (KB-5HUW, live, checked 2026-09-23)
- CTS is a control-plane audit log covering tenant API calls, console actions and IAM events. A window with no traces therefore bounds an incident to the guest operating system. (KB-7FCF, live, checked 2026-07-29)
- GET /v3/{project_id}/traces on the CTS endpoint in eu-de with trace_type=system, service_type, from and to in epoch milliseconds and limit=100 returns per trace the trace_name, resource_type, resource_name, HTTP code and trace_rating. That is enough to rebuild the order and outcome of a terraform apply or destroy, call by call, after the fact. (KB-A5RP, live, checked 2026-10-06)
- The CTS trace query API GET /v3/{project_id}/traces serves about seven days of history. limit maxes out at 200 per page and meta_data.marker is passed back as next to page further into the past. (KB-AB5E, live, checked 2026-07-29)
- CTS system traces are read with GET /v3/{project_id}/traces, using trace_type=system, limit, from and to as epoch milliseconds, and resource_id to filter a single resource. (KB-AK3I, live, checked 2026-07-31)
- An OBS setBucketPolicy call became visible in the CTS trace query about two to three minutes after it happened: the query returned nothing at first and the trace after a little over two minutes of polling every 30 seconds. (KB-FYVH, live, checked 2026-09-23)
- Cloud Trace Service keeps traces queryable through its API for 7 days in eu-de. An event older than that returns no trace, and is readable later only if an authorized OBS transfer or an enabled LTS forwarding was already active when the event happened. (KB-GJKP, live, checked 2026-07-31)
- A CTS event notification with operation_type customized requires an explicit operations list naming service_type, resource_type and trace_names, and then publishes matching traces to an SMN topic. (KB-GWL5, live, checked 2026-07-17)
- CTS traces record control-plane API actions. In a review after a suspected guest compromise the CTS record was complete for API actions and clean, while what happened inside the guest operating system was not answerable from it. (KB-JBYB, live, checked 2026-07-29)
- CTS writes hash-chained digest files only for a tracker that has OBS transfer configured together with the opt-in trace-file verification switch. The digest signature is SHA256withRSA and the file hashes are MD5. (KB-KVR7, docs, checked 2026-09-01)
- GET /v3/{project_id}/traces?trace_type=system on the CTS endpoint returns the operation vocabulary of a service, including operations that have no published API path. (KB-LYUM, live, checked 2026-09-10)
- CTS traces can be filtered with trace_type=system plus a from and to millisecond window, and narrowed by resource_id for one resource or by service_type, for example IAM to read the full identity trail of new users, credentials, agency grants and logins. (KB-M4UN, live, checked 2026-07-29)
- A customized CTS key event notification on OBS setBucketPolicy with the advanced filter resource_name = {bucket} delivered a mail through its SMN topic to a confirmed email subscription when that bucket's policy was written. No access policy on the SMN topic was needed for CTS in the same account. (KB-MQNL, live, checked 2026-09-23)
- The mail of a CTS key event notification states times as GMT+0100 even in German summer time: a trace at 15:14:22 UTC was shown as 16:14:22 GMT+0100. The mail carries the full trace, including the user name, the account and project ids and the source IP. (KB-MV5W, live, checked 2026-09-23)
- GET /v3/{project_id}/traces?trace_type=system&service_type=VPC on cts.eu-de.otc.t-systems.com returns the system traces for EIP work. The traces createEip, batchUpdateEipTags and deleteEip appeared about 20 seconds after the corresponding API call. (KB-NPWT, live, checked 2026-07-17)
- A CTS trace query filters by service_type only, so record counts over a time window measure all tenant activity rather than one procedure. In one window, 61 of 167 IMS records were queryImage. (KB-NY2U, live, checked 2026-09-02)
- GET /v3/{project_id}/trackers on the CTS endpoint answers HTTP 200. A tracker carries lts.is_lts_enabled, obs_info for transfer of traces to an object storage bucket and is_support_validate for trace file integrity, and these three are off by default. (KB-O4MB, live, checked 2026-07-02)
- A CTS trace routed to SMN and then to FunctionGraph released a non-compliant EIP about four seconds after its creation in eu-de. (KB-O6VO, live, checked 2026-07-17)
- POST /v3/{project_id}/notifications refuses a notification_name with hyphens with error cts.0007 'Notification name verify failed' and accepts underscores. A customized notification with an SMN topic and an advanced filter such as resource_name = {name} or resource_id = {id} with condition AND is created with status enabled and type smn. (KB-PHG6, live, checked 2026-09-23)
- Setting is_obs_created true in PUT /v3/{project_id}/tracker did not create a bucket or change obs_info in eu-de, although the call answered 200. (KB-R5XP, live, checked 2026-09-23)
- A CTS trace query with resource_type=security-group-rule returned zero traces for security group rule changes made minutes earlier, while older time windows in the same tenant returned complete results. (KB-RMYI, live, checked 2026-07-29)
- In a chain of CTS event notification to SMN to FunctionGraph, the remediating API call was recorded in CTS about four seconds after the event that triggered it. (KB-SLEN, live, checked 2026-07-17)
- With an existing bucket in the same account and is_obs_created false, PUT /v3/{project_id}/tracker switches the trace transfer to that bucket. The tracker then shows status enabled and is_authorized_bucket false, yet trace files arrived in the bucket within about a minute with no bucket policy set. (KB-TCSN, live, checked 2026-09-23)
- GET /v3/{project_id}/trackers returns the system tracker with status, lts.is_lts_enabled and obs_info fields including is_authorized_bucket and is_obs_created. Those fields show whether trace archiving to OBS or LTS is really active. (KB-TU5O, live, checked 2026-07-31)
- CTS records OBS bucket-policy changes as setBucketPolicy and deleteBucketPolicy with resource_type bucket and the bucket name as resource_name. IAM createCredential traces carry the new access key id as resource_id and do not name the user; updateUser and login traces carry the target user's id as resource_id. (KB-UWP4, live, checked 2026-09-23)
- CTS shows platform-internal actors beside the tenant's own identities: an op_service account materializes resources started from the console, and any agency created in the tenant appears as an actor too. Both are normal traffic in the audit trail. (KB-V232, live, checked 2026-07-29)
- In TCP eu-de on 2026-09-25 the documented CTS tracker queries GET /v3/{project_id}/trackers and GET /v1.0/{project_id}/tracker return the tracker and the trace listing GET /v3/{project_id}/traces responds normally. A GET on the singular path /v3/{project_id}/tracker, which the API reference defines only for POST and PUT, answers HTTP 404. (KB-VKNI, live, checked 2026-09-25)
- CTS recorded a manual switchover path across services: in a seven hour window CBR wrote 19 traces, IMS 167, ECS 129 and EVS at least 200, which is the page limit rather than a count. Each record holds actor, domain, source IP, time, resource and code. (KB-W44W, live, checked 2026-09-02)
- A CTS trace carries user.name, source_ip, trace_name for the action (createServer, deleteEip, createCredential), trace_rating with values normal, warning or incident, trace_type with values ApiCall, ConsoleAction or SystemAction, and code. (KB-YVOM, live, checked 2026-07-29)
- CTS holds a 7 day trace window for a control plane review. Traces can be read tenant wide, filtered by resource_id for one resource, or by service_type, for example IAM, to see new users, credentials and agency grants. (KB-YXTL, live, checked 2026-07-29)
